doc; this file covers sequencing only. Each milestone gets its own detailed plan in
`docs/plans/`, written just before work on it starts, and ships as one branch / PR.

## Notes

- **Math is tested with synthetic data.** Build inputs with known answers (e.g. 28
  elapsed days of intake at 2,000 kcal, bracketed by morning weights falling exactly
  0.5 kg/week → TDEE estimated from logs = 2,550 kcal at 7,700 kcal/kg). Include
  variable intake, missing totals, and water shifts; see milestone 2's tests.
- **Dev data for the dashboard.** An optional `scripts/seed_dev_data.py` that writes ~60
  days of fake entries to a separate dev database, so milestone 5 isn't built against an
  empty DB. Fold into milestone 5 if useful.
- **Open questions** from the requirements (display rounding, smoothing factor, TDEE
  window, energy density per unit) come up in milestones 2 and 5. Decide them there.

## Decisions

- **Package name stays `tdee_calculator`** (`src/tdee_calculator/`, as created by
  `uv init --package`). The requirements doc's `tdee/` layout maps onto it one to one.
- **Spreadsheet import is a nice-to-have, not v1.** There is no existing data to import.
- **SQLAlchemy 2.0 ORM (sync) + Alembic instead of stdlib `sqlite3`.** The app is meant
  to keep growing, so models and autogenerated migrations are worth the extra dependency.
  Migrations run automatically at startup, after the backup. `calc.py` still takes plain
  data, not ORM objects, so the math stays independent of the database.
- **SQLite, not Postgres.** It's a single-user, local app: SQLite needs no server (so
  `./run.sh` stays one command), keeps all data in one file (backups and moving machines
  are file copies), and makes tests trivial (a fresh DB per test in a temp dir). One row
  a day is nowhere near its limits. Postgres becomes worth it only with concurrent
  writers, multiple app servers, or managed hosting. Because access goes through
  SQLAlchemy and Alembic, switching later is mostly a connection-string change plus a
  one-time data copy. To keep that cheap: no raw SQLite-specific SQL outside `db.py`.
- **Local time everywhere.** The app runs on your machine, so its clock and time zone
  are treated as correct. Timestamps, entry dates, and backup filenames all use naive
  local time from `clock.py`, the only module that reads the clock. Revisit (store UTC
  and convert for display) only if the app is ever hosted for users in other time zones.

## Nice-to-haves (after v1)

- One-time spreadsheet import (weekly grid `.xlsx`, typed values only, `source = 'spreadsheet'`).
- Postgres, if the hosting reach goal brings multiple users (see the SQLite decision above).
- Everything under "Reach goals" in the requirements doc.
